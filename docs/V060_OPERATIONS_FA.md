# DNS Unified Control 0.6 — راهنمای نصب، ارتقا، کلاینت و عیب‌یابی

این سند همه مراحل فنی اجرای پروژه در گفتگوی نصب VPS را در یک محل گردآوری می‌کند. پنل **مدیر** ۹ روش است، اما **فقط یک موتور در لحظه روی UDP/53** می‌تواند فعال باشد. تا پیش از آزمون واقعی کلاینت، یک وضعیت `ready` یا `active` فقط سلامت فایل‌ها / سرویس systemd را نشان می‌دهد.

## وضعیت نمونه فعلی (پس از نصب 0.5)

- Ubuntu 24.04 / یک هسته CPU / حدود ۹۶۱ MiB RAM / ۲ GiB swap.
- Zone: `m2m.diy` و IPv4 مثال: `188.132.174.249`.
- `ns.m2m.diy A 188.132.174.249`، نه NS مجزا: `m,r,d,n,v,s,i,c,x.m2m.diy NS ns.m2m.diy`.
- رکوردها با Cloudflare DNS-only ساخته شدند و واگذاری آنها مستقیماً روی Nameserverهای authoritative تأیید شد.
- پنل روی `127.0.0.1:8088` و Caddy روی TCP 80/443 (HTTP/3 برای listener مربوط به پنل غیرفعال)؛ TLS صادرشده از Let's Encrypt برای `panel.m2m.diy`.
- DNSTT Go server ساخته شد، `ready=true` و `systemd active`، UDP/53: `*:53`، هدف اولیه `127.0.0.1:22`.
- **گواهی محلی HTTPS و TOTP موفق بودند؛ ارتباط DNS recursive از سمت کلاینت هنوز آزمایش نشده است.**

## ارتقای امن بدون نصب مجدد

1. بسته ZIP نسخه ۰.۶ را از سیستم شخصی به `/root/` VPS منتقل کنید. نام بسته `DNS-Unified-Control-v0.6.0.zip` است.
2. روی VPS دستورها:

```bash
cd /root
unzip -oq DNS-Unified-Control-v0.6.0.zip
cd /root/dns-unified-control
sudo bash upgrade.sh
systemctl is-active dns-unified-web.service dns-unified-agent.socket dns-unified@dnstt.service caddy
```

`upgrade.sh` قبل از جایگزینی فایل‌های برنامه یک backup از کد در `/root/` می‌گیرد، فایل‌های رمز و TOTP و کلیدهای موتور را حفظ می‌کند، تنظیمات Cloudflare/Caddy و DNS سیستم را دست نمی‌زند و `dns-unified@dnstt` فعال را ریستارت نمی‌کند. فقط Web/Agent برای بارگذاری کد جدید ریستارت می‌شوند. **نکته:** اگر در آینده قالب `install.sh` تغییر کرد، قبل از اجرا diff را مطالعه کنید.

## پنل جدید

زبانه **«راه‌اندازی و کلاینت‌ها»** شامل انتخاب هر ۹ موتور، راهنمای نسخه، وضعیت آماده‌بودن، وضعیت نصب و ساخت بسته، پارامتر resolver و local port، دستور کلاینت، آزمون TCP، دانلود ZIP راهنما برای همه روش‌ها و ابزار بررسی سلامت VPS است.

برای DNSTT دکمه «ساخت بسته کلاینت» باعث کامپایل فایل ELF لینوکس `amd64` از سورس بازبینی‌شده می‌شود، یک فایل ZIP شامل **باینری + کلید عمومی + README** تولید می‌کند، و لینک دانلود احراز هویت‌شده در پنل نمایش می‌دهد. کلید خصوصی DNSTT هرگز داخل ZIP نیست. برای SlipStream Rust، **فقط درصورتی که باینری کلاینت از قبل به طور جداگانه نصب شده باشد**، یک ZIP شامل executable و گواهی عمومی (pin) بسته‌بندی می‌شود؛ کامپایل خودکار Rust برای VPS کم‌حافظه به‌صورت پیش‌فرض پشتیبانی نمی‌شود.

همه موتورهای دیگر ZIP راهنما/پروفایل دارند؛ تولید خودکار باینری **فقط** برای موارد بررسی‌شده فعال است. ZIP «راهنما» را با «کلاینت قابل اجرا» اشتباه نگیرید. نصب سرور برای DNSTT، iodine، dns2tcp، MasterDnsVPN، VayDNS و Soar به‌صورت job مجزا و با تأیید کاربر تعریف شده؛ ممکن است کامپایل بسته به شاخه و وابستگی‌های بالادستی موفق نشود. NoizDNS و XDNS و SlipStream Rust نیازمند تأیید/نصب تخصصی هستند و دکمهٔ نصب خودکار ندارند.

سرور می‌تواند هنگام اجرای job CPU و دیسک مصرف کند. از اجرای چند build هم‌زمان جلوگیری می‌شود. یک build هرگز موتور را خودکار Start نمی‌کند. موتورهای در حال اجرا باید برای جایگزینی binary ابتدا با پنل متوقف شوند. خروجی job و شناسه source commit ثبت و از پنل قابل مشاهده است.

## Cloudflare از داخل پنل

در زبانه **DNS رکوردها** می‌توانید با توکن موقت محدود به Zone، ۱۰ رکورد را Preview و با تأیید صریح Apply کنید. Token به‌صورت موقت فقط در یک درخواست به Agent ارسال می‌شود؛ ذخیره نمی‌شود. دسترسی لازم:

- `Zone → Zone → Read`.
- `Zone → DNS → Edit` (به نسخه API و محدودیت Zone Resources توجه کنید).
- `Zone Resources → Specific zone → DOMAIN`.

HTTP 200 از endpoint `user/tokens/verify` فقط **فعال بودن توکن** را تأیید می‌کند؛ HTTP 403 در endpoint `/zones/{id}/dns_records` یعنی مجوز خواندن یا نوشتن DNS هنوز کافی نیست. روی Zone فعال و ثبت‌شده تست کنید.

اگر موتور فعال باشد، **مهاجرت Zone به نام دیگر** در پنل تا زمان توقف موتور رد می‌شود. رکورد‌های غیرمدیریت‌شده overwrite نمی‌شوند، اما Cloudflare چند درخواست جداست و اتمیک نیست: خطای وسط کار ممکن است باعث ایجاد بخشی از رکوردها شود. دوباره Preview کنید.

## تست واگذاری DNS در حضور موتور خاموش

تست رکورد NS از Recursive Resolver با `dig +short` ممکن است خالی باشد، چون Resolver برای پرس‌وجو از authoritative tunnel endpoint که خاموش است timeout می‌دهد. برای آزمایش درست **از Nameserver والد authoritative** سؤال کنید:

```bash
for parent in $(dig @1.1.1.1 m2m.diy NS +short); do
  dig @"$parent" d.m2m.diy NS +norecurse +noall +answer +authority
done
```

در این حالت باید `d.m2m.diy. IN NS ns.m2m.diy.` دیده شود. همچنین `dig @1.1.1.1 ns.m2m.diy A +short` باید IP عمومی سرور را برگرداند. این **عبور ترافیک تونل** را تأیید نمی‌کند.

## سیستم DNS و پورت ۵۳

`systemd-resolved` در Ubuntu معمولاً به `127.0.0.53:53` و `127.0.0.54:53` متصل است. نسخه فعلی مدیر Exclusive Mode اشغال هر `:53` را تداخل تلقی می‌کند. برای آزادسازی روی سرور فعلی، DNSStubListener در `/etc/systemd/resolved.conf.d/90-dns-unified.conf` خاموش و `/etc/resolv.conf` به `/run/systemd/resolve/resolv.conf` پیوند داده شد. **این کار روی VPSهای دیگر نباید بدون backup، DNS upstream و راه برگشت اجرا شود.**

```bash
ss -lntup | grep ':53' || true
readlink -f /etc/resolv.conf
getent ahostsv4 ubuntu.com
```

اگر موتور DNSTT فعال است `*:53` باید متعلق به `dnstt-server` باشد. UDP/53 باید در فایروال محلی و پنل ارائه‌دهنده VPS نیز مجاز باشد.

## DNSTT — کلاینت و آزمون واقعی

موتور فعلی `d.m2m.diy` را به `127.0.0.1:22` فورواد می‌کند؛ این **SOCKS5 نیست** و SSH داخلی را به همراه دارد.

- روی پنل به **راه‌اندازی و کلاینت‌ها → DNSTT → ساخت بسته کلاینت** بروید.
- ZIP را روی سیستم لینوکس شخصی دانلود/استخراج کنید، `chmod +x dnstt-client` بزنید.
- دستور کلاینت را از همان پنل کپی کنید؛ key عمومی ۶۴کاراکتری از فایل `server.pub` گرفته می‌شود.
- تست مستقیم IP/UDP/53 برای بررسی باز بودن مسیر: `-udp VPS_IP:53`.
- تست واقعی از Recursive DNS برای بررسی واگذاری: `-udp 1.1.1.1:53` یا `-udp 8.8.8.8:53`.
- برای تست TCP: `ssh-keyscan -T 35 -p 2222 127.0.0.1` (بعد از اجرای کلاینت با `127.0.0.1:2222`). کلید SSH نشان‌دهنده رسیدن TCP به سرویس SSH است، نه اثبات امنیت کلید میزبان؛ Fingerprint را از راه مستقل تأیید کنید.
- برای SOCKS: پس از احراز هویت SSH، یک اتصال SSH به پورت محلی DNSTT با `ssh -N -D 127.0.0.1:1080 -p 2222 USER@127.0.0.1` و سپس `curl -x socks5h://127.0.0.1:1080 https://api.ipify.org`.

اگر مستقیم کار کرد و recursive نه: مسیر resolver، NS authoritative، فایروال DNS و نرخ محدودسازی را بررسی کنید؛ تغییر IP تنها مشکل را حل نمی‌کند.

**امنیت:** خود DNSTT با رمز کاربر وارد نمی‌شود؛ SSH سرور باید با تنظیمات احراز هویت صحیح و ترجیحاً کلید شخصی محافظت شود. اتصال SSH را از دست ندهید و از کلید خصوصی `dnstt.key` حفاظت کنید.

## HTTPS، TOTP، CPU و رفع خطا

- خطای مرورگر `Server response was not JSON` یک خطای HTML/متن سمت سرور بود؛ `POST /api/login` به جای JSON، HTTP 500 می‌داد. ریشه: PermissionError در دسترسی به `/var/lib/dns-unified/mfa/web-mfa.json` به علت دسترسی `0700 root`. نصب‌کننده 0.6 حالا مالکیت `root:dns-unified` و مجوز `0710` برای پوشهٔ مادر را اعمال می‌کند و پوشه MFA همچنان `0700 dns-unified` است.
- HTTPS موفق: `curl -4sS -o /dev/null -w '%{http_code} %{ssl_verify_result}\n' https://panel.m2m.diy/` باید `200 0` بدهد. `curl -I` ممکن است 405 برگرداند، چون برنامه فقط GET را قبول می‌کند؛ این خطای TLS نیست.
- Caddy گواهی Let's Encrypt را دریافت می‌کند و HTTP/3 پنل عمداً غیرفعال است تا UDP/443 به‌صورت ناخواسته اشغال نشود. هشدار OCSP بدون endpoint به‌تنهایی به معنی گواهی نامعتبر نیست.
- TOTP: وجود فایل MFA شرط لازم است، اما برای تأیید کامل باید با کد معتبر وارد پنل شوید. هر ۱۰ کد بازیابی یک‌بار مصرف‌اند. دو رمز و توکن API که در مکالمه افشا شده‌اند باید تعویض/باطل شوند.
- CPU: نمودار ۱۰۰٪ لحظه‌ای را با `ps -eo pid,comm,%cpu,%mem --sort=-%cpu | head`, `uptime`, `free -h` مقایسه کنید. درصد CPU در `ps` میانگین بازه عمر پردازش است. نصب Go روی VPS ۱GB با swap امن‌تر است، اما swap جای RAM را نمی‌گیرد.
- APT: `nala fetch --https-only` تأخیر فایل Release را می‌سنجد نه پهنای باند واقعی. Mirror کند یا HTTP403 را با دانلود واقعی `.deb` بررسی کنید، منبع `noble-security` را حفظ کنید و Duplicate Sourceهای Ubuntu را اصلاح کنید.

## محدودیت‌ها و امنیت عملیاتی

این نسخه ۹ موتور را کاتالوگ می‌کند اما **تضمین نمی‌کند هر ۹ upstream سالم، سازگار یا کامپایل‌شدنی هستند**. NoizDNS fork، XDNS و MasterDnsVPN نیاز به قالب سازگار و بررسی واقعی upstream دارند؛ DoH/DoT/DoQ صرفاً روش حمل DNS هستند. دسترسی عمومی پنل را به IPهای مجاز/Cloudflare Access محدود کنید؛ توکن‌ها و رمزها را در چت یا اسکرین‌شات نفرستید. ZIP قابل‌دانلود کلاینت حاوی هیچ کلید خصوصی یا رمز مشترک نیست.


### رفع خطای ساخت کلاینت در 0.6.0

در نسخه 0.6.0 سرویس مستقل ساخت کلاینت ممکن است خطای `go: module cache not found: neither GOMODCACHE nor GOPATH is set` بدهد. نسخه 0.6.1 برای همه ساخت‌های Go در Worker مسیرهای صریح و خصوصی `GOPATH`، `GOMODCACHE`، و `GOCACHE` را در `/var/cache/dns-unified/go` می‌سازد. نیاز به تغییر دستی `.bashrc` یا راه‌اندازی مجدد موتور فعال نیست. پس از `bash upgrade.sh` ساخت بسته کلاینت DNSTT را از پنل تکرار کنید.
