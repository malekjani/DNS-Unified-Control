# نسخه 0.9.1 — Soar محدودشده به Dante، یک کلاینت بومی، بدون Gateway

این انتشار فقط جریان کامل **Soar** را در وب‌پنل خودکار می‌کند. موتورهای دیگری که Provision آنها هنوز ناقص است، در این نسخه به‌اشتباه آماده تلقی نمی‌شوند.

## مسیر ارتباط

v2rayN / FoxyProxy → SOCKS5 127.0.0.1:2080 با همان نام کاربری/رمز Dante → `soar-client` روی Debian → Resolver DNS → `duc-soar-server` روی VPS (Exclusive UDP/53) → **فقط** 127.0.0.1:1080 (Dante مشترک با احراز هویت) → اینترنت

`soar-client` یک باینری کامپایل‌شده Go است که مستقیماً از کتابخانه رسمی `github.com/getlantern/soar` استفاده می‌کند. این باینری **به‌طور اختصاصی داخل پروژه ساخته شده** و نباید به‌اشتباه باینری رسمی Rust `getlantern/soar-rs` معرفی شود. این برنامه خود کلاینت تونل است؛ سرویس SOCKS دیگر یا Gateway پایتونی اجرا نمی‌کند. سرویس اصلی SOCKS فقط Dante سمت VPS است.

## ارتقا از 0.9.0

1. ZIP کامل را به `/root/` VPS انتقال بده، سپس با مسیر `/root/dns-unified-control` استخراج کن و `bash upgrade.sh` را اجرا کن.
2. این ارتقا **به‌خودی‌خود Soar را نصب/فعال نمی‌کند** و موتور DNS فعال را نباید ری‌استارت کند.
3. از داخل پنل `راه‌اندازی و کلاینت‌ها` موتور `Soar` را انتخاب کن.
4. `نصب Soar و تولید کلید` را انتخاب کن. Job جداگانه با ریشه معتبر `getlantern/soar` کار می‌کند؛ آخرین commit استفاده‌شده را در گزارش ثبت می‌کند. کلید خصوصی سرور فقط روی VPS ذخیره می‌شود، قابل دانلود نیست و اگر موجود باشد حفظ می‌شود.
5. `ساخت کلاینت مستقیم Linux` را بزن و بعد `دانلود کلاینت Soar` را انتخاب کن. بسته شامل `soar-client`، `server.pub`، راهنمای دستور و اطلاعات commit است. **رمز Dante در بسته وجود ندارد**.
6. از پنل `بررسی واگذاری NS` را بررسی کن؛ دامنه Soar در این پروژه `s.m2m.diy` است. Delegation پیش از اتصال واقعی به‌تنهایی اثبات تونل نیست.
7. قبل از تغییر موتور در Exclusive Mode، مطمئن شو مسیر SSH مدیریتی مستقل داری. کلاینت قبلی را روی Debian متوقف کن و بعد موتور Soar را در پنل فعال کن.
8. دستور خروجی پنل را روی Debian اجرا کن (مثال):

```bash
./soar-client -zone s.m2m.diy -pubkey PUBLIC_BASE64_KEY -resolver 1.1.1.1:53 -listen 127.0.0.1:2080 -forward 127.0.0.1:1080
```

سپس در v2rayN/FoxyProxy آدرس `127.0.0.1` و پورت `2080` و **همان نام کاربری/رمز Dante** را وارد کن.

## آزمون بدون JSON

```bash
read -r -p 'Dante username: ' U
read -rs -p 'Dante password: ' P; echo
curl -4 --connect-timeout 25 --max-time 120 --socks5-hostname 127.0.0.1:2080 --proxy-user "$U:$P" https://api.ipify.org
a=$?; unset U P; exit "$a"
```

اگر `188.132.174.249` بازگردانده شود، مسیر خروج اینترنت همین VPS را نشان می‌دهد. برای سنجش پایداری/کارایی آزمایش‌های طولانی و چندسروری جداگانه ضروری است.

## چرا حالت Fixed Backend؟

فرمان رسمی `soar-server` به‌طور پیش‌فرض به مقصدهای عمومی پورت‌های 80 و 443 اجازه می‌دهد و `-allow-private` گستره خطر دسترسی به شبکه خصوصی را زیاد می‌کند. برای Soar در این پروژه، سرور `duc-soar-server` با `ServerConfig.Dial` سفارشی فقط به `127.0.0.1:1080` اتصال می‌زند و **تمام آدرس‌های دیگر** را رد می‌کند. بنابراین سرور Soar یک پراکسی مقصد دلخواه نمی‌شود؛ خروج اینترنت همچنان نیازمند احراز هویت Dante است. البته کلید عمومی Soar مخفی نیست و باید سطح سوءاستفاده/DoS مانیتور شود.

## محدودیت‌ها

- فقط Linux amd64 برای بسته کلاینت آماده می‌شود. ساخت برای Windows، Android و معماری‌های دیگر هنوز خودکار نشده است.
- اگر کاربر پورت جداگانه‌ای برای Soar بخواهد، پیاده‌سازی فعلی عمداً به جز `127.0.0.1:1080` اجازه Backend سفارشی نمی‌دهد تا به سرویس‌های محلی بدون احراز هویت دسترسی باز نشود. این امکان فقط پس از تعریف Backend دارای احراز هویت و بررسی امنیتی باید اضافه شود.
- وجود باینری قدیمی عمومی `soar-server` به معنای فعال‌شدن حالت امن نیست؛ باینری مطلوب `duc-soar-server` است.
- نصب باینری و کلیدها **هیچ سرویسی را خودکار روشن نمی‌کند**. تغییر موتور فقط از Exclusive Mode انجام می‌شود.
- به‌دلیل پیش‌انتشاربودن پروتکل Soar، سرور و کلاینت از یک snapshot منبع رسمی کامپایل می‌شوند؛ commit آن در گزارش ثبت می‌شود.
- تست‌های بسته شامل تست Python، JavaScript، فرمت Go و کامپایل با API شبیه‌سازی‌شده بوده‌اند؛ کامپایل واقعی کتابخانه Go و آزمون زنده VPS در زمان ساخت این ZIP امکان‌پذیر نبود.
